# Local DataHub + warehouse substrate

The repository owns a concept-neutral development substrate. From a clean
clone:

```bash
docker compose up
```

This starts DataHub OSS, a writable Postgres warehouse, and a one-shot
metadata ingestion job. The warehouse is initialized from
`infra/warehouse/init.sql`; ingestion uses
`infra/datahub/postgres.yml`. No mock metadata or pre-baked DataHub response is
used.

## Services

| Service | Address / purpose |
| --- | --- |
| DataHub UI | http://localhost:9002 (`datahub` / `datahub`) |
| DataHub GMS / GraphQL | http://localhost:8080 |
| Postgres warehouse | `localhost:5432`, database `warehouse`, `agent` / `agent` |
| `metadata-ingestion` | Profiles and writes `ecommerce` metadata into DataHub, then exits successfully |

The remaining containers are DataHub's required local dependencies: Kafka,
MySQL, OpenSearch, and the one-shot system upgrade.

## Verify real warehouse data

```bash
docker compose exec warehouse \
  psql -U agent -d warehouse \
  -c 'select * from ecommerce.customer_order_summary order by customer_id;'
```

The `agent` role owns the warehouse and can both read and write it. For
example, an agent can insert a row and roll it back without mutating the
durable seed:

```bash
docker compose exec warehouse psql -U agent -d warehouse -c \
  "begin; insert into ecommerce.customers
   (customer_id, email, country_code) values
   (999, 'agent@example.com', 'US'); select email from
   ecommerce.customers where customer_id = 999; rollback;"
```

## Query the live DataHub graph

`scripts/query-seeded-entity.sh` sends this agent-authored query to
`POST /api/graphql`:

```graphql
query SeededWarehouseEntity($urn: String!) {
  dataset(urn: $urn) {
    urn
    name
    platform {
      name
    }
    schemaMetadata {
      fields {
        fieldPath
        nativeDataType
      }
    }
  }
}
```

Run it with:

```bash
bash scripts/query-seeded-entity.sh
```

The result is generated by GMS from metadata that the ingestion container
read from the live Postgres system.

## Lifecycle and resources

```bash
docker compose down
docker compose down --volumes  # destructive clean reset
```

The full stack needs roughly 4 CPUs, 8 GB RAM, and several GB of Docker image
storage. First startup takes longer while images download; subsequent starts
reuse them.
